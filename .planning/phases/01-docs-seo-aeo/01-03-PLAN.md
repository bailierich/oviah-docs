<objective>
Add the two JSON-LD schema components and wire them into article rendering.

Purpose:
- `Article` JSON-LD lets Google show enhanced search results (publisher, headline) and helps AI engines extract canonical metadata.
- `FAQPage` JSON-LD is the single highest-leverage AEO move: when present, AI engines (especially Perplexity and Google AI Overviews) extract Q&A pairs verbatim into answer cards, citing the source.

Output:
- `components/ArticleSchema.jsx` — named export `ArticleSchema` rendering an `Article` `<script type="application/ld+json">`.
- `components/FAQSchema.jsx` — named export `FAQSchema` rendering a `FAQPage` `<script type="application/ld+json">`.
- `components/ArticlePage.jsx` — modified to render `<ArticleSchema>` always, and `<FAQSchema>` conditionally when `frontmatter.faq` is a non-empty array.

Depends on Plan 01 because `ArticleSchema` consumes `frontmatter.title`, `frontmatter.description`, and the `slug`/`category` route params — all of which Plan 01 stabilizes via the normalized frontmatter contract.
</objective>

<discretionary_resolutions>
1. **Where to render the schemas** (CONTEXT discretion): The article route is `app/help/[category]/[slug]/page.jsx`, but it delegates rendering to `components/ArticlePage.jsx`. The page receives `params` (which contain category + slug) but `ArticlePage` does not currently get the slug — it only gets `frontmatter` and `content`. RESOLUTION: Modify `app/help/[category]/[slug]/page.jsx` to pass `category` and `slug` to `ArticlePage`, and render the schema components inside `ArticlePage` alongside the article body. This keeps the schema next to the rendered content and avoids creating a parallel rendering surface.

2. **`ArticleSchema` URL pattern**: Same correction as Plans 01 and 02 — the URL is `https://docs.oviah.com/help/${category}/${slug}`, NOT the PRD's flat `/help/${slug}`. The component takes both `category` and `slug` props.

3. **`FAQSchema` data source**: D-07 specifies `frontmatter.faq` must be an array of `{ q, a }` objects. NO existing article currently has `faq` frontmatter (verified by planner via grep). That's fine — `FAQSchema` will simply never render until an author adds `faq` frontmatter to an article. This plan does NOT add `faq` frontmatter to any article (that's authoring work, out of scope per PROJECT.md). It only adds the rendering plumbing so future authoring "just works".

4. **`.jsx` not `.tsx`**: Match the rest of the project. No TypeScript types on props. Use plain function components.

5. **`dangerouslySetInnerHTML`**: Per D-06 and D-07, both schemas use `dangerouslySetInnerHTML` with `JSON.stringify(...)`. This is the standard React pattern for inline JSON-LD. Do NOT use a `<script>{...}</script>` template literal — React will escape it.
</discretionary_resolutions>

```jsx
export function FAQSchema({ questions }) {
  return (
    <script
      type="application/ld+json"
      dangerouslySetInnerHTML={{
        __html: JSON.stringify({

          '@type': 'FAQPage',
          mainEntity: questions.map(({ q, a }) => ({
            '@type': 'Question',
            name: q,
            acceptedAnswer: { '@type': 'Answer', text: a },
          })),
        }),
      }}
    />
  );
}
```

Locked field-by-field per D-07:
- `'@context'`: `'https://schema.org'`
- `'@type'`: `'FAQPage'`
- `mainEntity`: array produced by mapping `questions` to `Question` objects
- Each Question has: `'@type': 'Question'`, `name: q`, `acceptedAnswer: { '@type': 'Answer', text: a }`

Notes:
- Named export `FAQSchema`.
- The `questions` prop shape is `{ q: string, a: string }[]` per D-07. The component does NOT validate the shape — the calling site (Task 3) is responsible for only passing this when the data is present.
- `FAQSchema` is rendered ONLY when the article has `frontmatter.faq` that is an array AND non-empty. Task 3 enforces this guard.
- No TypeScript types.
